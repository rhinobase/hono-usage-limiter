## Long-term Knowledge

### Architecture

<!-- lore:019f033c-4bd6-7865-8bd8-9af861df9ac8 -->
* **hono-credit package structure: dual CJS/ESM with /memory subpath export**: Package: \`hono-usage-limiter\` v0.1.0, repo \`rhinobase/hono-usage-limiter\`. Main entrypoint: \`src/index.ts\` (exports types, UsageManager, usageManager middleware). Separate entrypoint \`src/memory.ts\` for \`/memory\` subpath — dual CJS/ESM: \`dist/memory.{js,cjs,d.ts,d.cts}\`. Built with pkgroll. Key types: \`UsageBucket\`, \`UsageStore\`, \`UsageManager\`, \`UsageStatus\`, \`UsageEnv\`, \`UsageManagerConfig\` (field: \`defaultUsage\`). Rolling window bucket model with optimistic gate. Release system: craft-based with 5 workflow files (\`.craft.yml\`, \`release.yml\`, \`package-artifacts.yml\`, \`publish.yml\`, \`changelog-preview.yml\`) adapted from freestyle SDK pipeline pattern.

<!-- lore:019f033c-4bd0-7db2-b646-09ffb156cbfa -->
* **hono-credit: DB-agnostic credit management via CreditStore adapter interface**: hono-usage-limiter is Hono-focused but database-agnostic — users implement the \`UsageStore\` interface with 5 methods (\`getBucket\`, \`createBucket\`, \`updateBucket\`, \`deduct\`, \`getLedger\`). No SQL migrations are shipped. A \`MemoryStore\` is included for testing (exported via \`/memory\` subpath). The library injects a single \`UsageManager\` object onto Hono context as \`c.get('usage')\` via \`usageManager()\` middleware. Handlers control all logic by calling \`usage.check()\`, \`usage.deduct()\`, \`usage.getBalance()\`, \`usage.getHistory()\`, \`usage.reset()\`, \`usage.provision()\`. Middleware only injects — it does not auto-deduct. Known design issues: \`MemoryStore.getBucket()\` returns a mutable reference (fix: spread \`{ ...bucket }\`). \`UsageDeductResult.success\` is always \`true\` — no false path. \`keyGenerator\` typed as \`(c: unknown)\` forces consumer casts. \`totalConsumed\` JSDoc says 'lifetime' but resets on window/refill/provision — actual meaning is 'current window'.

### Gotcha

<!-- lore:019f07ae-b9eb-7e7c-b3ed-2264ab17d0ee -->
* **hono-usage-limiter: totalConsumed JSDoc says 'lifetime' but resets on window/refill/provision**: Trap: \`UsageBucket.totalConsumed\` JSDoc (src/types.ts) says 'lifetime of this bucket', implying it accumulates forever. Fix: \`reset()\`, auto-refill (\`resolveBucket()\`), and \`provision()\` all set \`totalConsumed: 0\` — actual semantics are 'current window'. \`UsageBalanceInfo.totalConsumed\` JSDoc correctly says 'current window'. The \`UsageBucket\` JSDoc is misleading and should be corrected before publish.

<!-- lore:019f033c-4bd4-7d47-83d4-bd15de15ebf4 -->
* **MemoryStore getLedger: sort by insertion index, not timestamp**: Trap: sorting ledger entries by \`created\_at\` timestamp (Date.now()) looks correct for newest-first ordering. Fix: entries created in rapid succession (e.g. in tests) get identical timestamps, making the sort unstable and tests flaky. \`MemoryStore.getLedger\` must sort by reversed insertion index instead of timestamp. Confirmed bug in \`src/memory.ts\` caught by test \`MemoryStore > should return ledger entries newest first\`. Note: class is now \`MemoryStore\` implementing \`UsageStore\` (renamed from \`CreditStore\`).

<!-- lore:019f07ae-b9e9-75e0-9929-c4d70f31d7bf -->
* **MemoryStore.getBucket returns mutable reference — silent state corruption**: Trap: \`MemoryStore.getBucket()\` (memory.ts) returns the actual object stored in the internal Map, which looks fine since it's typed as \`UsageBucket\`. Fix: consumer mutation (e.g. modifying returned bucket fields) silently corrupts store state because it's the same reference. Fix by returning \`{ ...bucket }\` spread. This is a pre-publish bug in hono-usage-limiter v0.1.0.

<!-- lore:019f079e-b492-75a2-98bb-9cf427bde55c -->
* **pkg-pr-new requires GitHub App installation — 404 on /check is not a code error**: Trap: \`pnpm exec pkg-pr-new publish "."\` failing with \`{"statusCode":404,"message":"There is no workflow defined for ..."}\` looks like a misconfigured workflow or wrong publish path. Fix: the pkg-pr-new GitHub App must be explicitly installed on the repo at https://github.com/apps/pkg-pr-new — it's not inherited from org-level installs. No code change needed. In hono-usage-limiter, the 'Release preview' CI workflow fails for this reason while 'CI Tests' passes fine.

### Preference

<!-- lore:019f07c9-4af0-706a-afe1-b16e13218213 -->
* **Always confirm architectural constraints before proposing solutions**: When reviewing or designing code, the user explicitly confirms fundamental architectural constraints (e.g., 'store is always a pre-constructed instance', 'D1 bindings are always request-time in Cloudflare Workers', 'store is never re-evaluated') before accepting or rejecting proposed changes. The user expects the assistant to surface these constraints as questions or findings, then waits for explicit confirmation before proceeding. Do not assume or infer runtime behavior — always surface architectural assumptions and get the user to confirm them as facts before building on them.

<!-- lore:019f0350-70e5-7562-ac49-08a44d04ce9b -->
* **Always explore and read existing files thoroughly before making changes**: Before implementing or modifying anything, the user consistently requests (or the assistant performs) a thorough read of all relevant existing files — directory trees, config files, workflows, source files, and documentation. This applies whether starting a new feature, renaming a package, or understanding a release system. The user expects the assistant to fully understand the current state of the codebase (including stale/incorrect content) before proposing or applying any changes. Skipping this exploration phase is not acceptable — even when the task seems straightforward.

<!-- lore:019f07c6-fe0a-75a2-b9c3-3a09ef8ae82e -->
* **Always identify and flag request-time vs. registration-time initialization conflicts**: When reviewing middleware or library architecture, the user consistently identifies and raises the problem of resources (like \`c.env.DB\`) that are only available at request time being required at middleware registration time. The user proactively proposes concrete solutions (factory/lazy pattern or deferred initialization inside the middleware) and asks whether the existing API supports the pattern before proceeding. When implementing or reviewing stores/adapters, always consider whether constructor dependencies are available at registration time, and prefer or flag support for a factory/lazy initialization pattern (e.g., \`store: (c) => new D1Store({ db: c.env.DB })\`) to handle environment-bound resources.

<!-- lore:019f079e-b4ce-7a42-8c41-acd8590d90e4 -->
* **Always investigate CI failures by diagnosing root cause before proposing fixes**: When CI is failing, the user expects a thorough diagnostic process: identify which specific workflow/step failed, extract the exact error message, check environment details (runner, Node version, tool versions), and pinpoint the root cause (e.g., missing GitHub App installation, misconfiguration) before proposing a fix. The user wants the fix clearly distinguished as a code change vs. an external action (e.g., installing a GitHub App). Fixes should be minimal and targeted — only address the confirmed root cause, not unrelated issues observed during investigation.

<!-- lore:019f07ae-ba25-7490-a25b-b2e0d0c5bb24 -->

This review covers: final file states with line counts, all exports and their types, key implementation details (method signatures, guards, defaults), test coverage (describe blocks, test counts, what each test verifies), and any remaining issues. The assistant should display every changed file's confirmed final state in detail, not just a summary. This happens as a checkpoint step after a batch of changes and before any git or publish operations.
